# Local Workbench owner — terminal-free development service

This is a **development-checkout** systemd user service, not another Pi process or a terminal emulator. The Omarchy Companion and Pi observer are installed separately. The owner keeps one verified Team Runner, observer bridge and owner-only socket alive independently of the workbench dock, Pi terminals and any interactive terminal. Its source is `manual/omarchestra-workbench-owner.service` and it requires this checkout and the installed `mise` Node `latest` link to remain available. No service is enabled by the disposable gate or by a bar click.

## Current Assignment-loop upgrade boundary

The Assignment runtime requires store schema 10. A schema-9 installed root must not be restarted as an upgrade attempt. The explicit offline `manual/workbench-store-upgrade.ts --plan|--apply` command now supports exact schema 9→10, after the separate legacy receipt migration has produced a verified v3 receipt. It requires explicit state/runtime/evidence paths and exact plan-digest authorization for apply. Preserve all existing history, fences and incomplete evidence; no empty replacement root, automatic restore or manual schema editing. See the [live-readiness checkpoint](../docs/reviews/assignment-loop-live-readiness.md) for gates and application order. The real root has **not** been migrated. Native Stop, handoff, Resume/Retry and stopped-writer release now pass disposable entry-point gates; loaded Pi/Companion verification and the live task remain unperformed. Source Companion 0.15.0 requires an explicit receipt-backed update from installed 0.14.0 and a loaded-component check, not merely a matching file version. The existing receipt migration and Companion setup require a real operator TTY; do not synthesize confirmation or bypass those entry-point guards.

## Read-only preflight and exact live authorization

1. The operator explicitly authorized enabling the service without starting it during setup, and requested on-demand starting through the bar button. Do **not** treat having clicked the bar, installed the plugin or typed `y` for its receipt as authorization to install any other background service.
2. Inspect `systemctl --user cat omarchestra-workbench-owner.service` and `~/.config/systemd/user/omarchestra-workbench-owner.service`: refuse existing unknown service state or unexpected symlinks; don't overwrite it.
3. Confirm no owner is listening at `$XDG_RUNTIME_DIR/omarchestra-workbench-phase2-live/omarchestra-workbench.sock`, inspect the exact owned state and runtime roots, and ensure no stale named sockets would block startup. Never remove unknown or stale paths by name. The owner's exclusive SQLite lock must remain the single authority; no second owner or hidden Pi may be created.
4. Validate `systemd-analyze --user verify manual/omarchestra-workbench-owner.service` and the full disposable gate. Then run `systemctl --user enable "$PWD/manual/omarchestra-workbench-owner.service"` from the fixed repository root, **without `--now`**. This registers the exact service for later login and on-demand bar activation but must not start the owner during setup. Use systemd's supported unit linking/enablement, not manual changes to Omarchy `shell.json` or the bar widget.
5. Check `systemctl --user is-enabled omarchestra-workbench-owner.service` and confirm `is-active` is still inactive. The bar's exact installed launcher may then request `systemctl --user start omarchestra-workbench-owner.service` after validating the installed unit identity; it waits for the real owner endpoint and opens the dock. After a physical click check `is-active`, the read-only `node --experimental-strip-types --experimental-sqlite packages/local-workbench-v1/runner/main.ts status --runtime-dir "$XDG_RUNTIME_DIR/omarchestra-workbench-phase2-live"`, loaded Companion generation, and in-dock Close → bar reopen. Check systemd's MainPID stays unchanged, no new Pi process is spawned, and no owner terminal exists. Report separately if any live UI step is not exercised.

The unit is attached to `graphical-session.target` and starts only in the user session, uses explicit already-owned state/runtime roots, does not use `RuntimeDirectory=` (which could delete guarded socket evidence on stop), and is bounded to three failed starts per minute. `Restart=on-failure` restarts unexpected owner failures, **not** a deliberate `systemctl --user stop`. An abnormal crash can leave named sockets; existing fail-closed socket ownership deliberately blocks automatic takeover rather than guessing which inode to delete. Check owner logs and perform exact evidence-backed recovery, never hide the failure by a fresh empty state directory. A graphical-login reboot recreates `$XDG_RUNTIME_DIR`; the v3 ownership receipt pins stable filesystem/inode identity while capturing private runtime and mount identity anew per owner lifetime. Historical v1 receipts that pinned `/run` inodes and v2 receipts that persisted reboot-sensitive device numbers must go through the bounded `manual/workbench-runtime-receipt-recovery.ts --plan` → interactive `--apply` migration **before** clearing any `start-limit-hit` failure. Preserve the exact old receipt outside the root. Never delete SQLite locks, reinitialize Project/Goal state or rewrite ownership JSON by hand to make the service start. Full-reboot recovery of a Pi/model session remains outside the MVP guarantee.

To stop the owner deliberately: `systemctl --user stop omarchestra-workbench-owner.service`. This does not kill Pi or remove the installed Companion. `systemctl --user disable --now omarchestra-workbench-owner.service` also disables future graphical-session startup; remove only the exact service link the operator actually installed, after inspecting it. When the owner is stopped and the exact unit is enabled, the bar may start **only that service** via systemd and wait for owner readiness. If the unit is absent, foreign, disabled or fails, report unavailability; never launch a terminal or agent. The service logs to the user journal (`journalctl --user -u omarchestra-workbench-owner.service`); no foreground owner window is needed. When the **versioned Companion release changes**, hide the current presentation, finish exact-plan plugin setup, restart the Omarchy shell, then restart this user service after confirming the old owner is idle. A long-lived owner keeps the old imported `WORKBENCH_PLUGIN_VERSION` until that service restart; a new loaded Companion version cannot be opened by it. Never restart a busy owner/Pi automatically or treat a version mismatch as success. The bar's one-shot launcher no longer emits desktop notifications on failure; it exits nonzero with an actionable reason in the caller/user journal.
