Durable workflows · Agent orchestration · Product fit

Could Trigger.dev or Inngest power Omarchestra?

Both platforms can run durable workflows and stream agent activity. The key question is whether they can do that while preserving Omarchestra’s execution-node, process, assignment, and acceptance authorities.

Research overview · Full Markdown note · No product or architecture decision

01 / Bottom line

Good adjacent engines—not drop-in Team Runners

For the current MVP: keep the Team Runner authoritative for Goals, Assignments, gates, artifacts, and workflow state. Keep visible Pi as the managed coding agent and Boomux as terminal-runtime owner.

Both products support streaming assistant responses and tool activity, so either could feed a future browser or Companion viewer. Streaming does not provide a native Pi TUI, persistent PTY, or Omarchestra control semantics.

02 / Omarchestra today

Preserve the authority boundaries

An external workflow engine can help execute jobs, but should not silently become the source of truth for the product’s domain state.

Omarchestra Companion

Renders projections and submits validated user intents.

↓
Team Runner on selected Execution Node — canonical authority

Goals, Assignments, gates, artifacts, writer policy, workflow state, and accepted transitions.

↓
Visible Pi + bridge

Conversation/model-session semantics and structured process facts.

Boomux

PTY/process lifecycle, terminal attachment, and resize.

↕
Optional Trigger.dev / Inngest adapter

Auxiliary jobs or stream events. Do not infer that an external worker is the visible Pi process.

Engine success is not gate acceptance

A successful task is not automatically accepted work; an LLM response is not gate evidence; a cancellation acknowledgement does not prove a process stopped.

Current product constraints

One Node per Goal, a single writer, visible interactive Pi for managed coding agents, and a Project Message Board that is structured coordination—not a transcript mirror.

See the MVP design, agent coordination, and remote execution boundary.

03 / Framework overviews

What each platform contributes

Trigger.dev

Durable task platform + AI Chat

Task code runs on Trigger.dev workers with queues, concurrency limits, retries, idempotency, waitpoints, traces, and Realtime streams. AI examples include batch fan-out, durable chat sessions, and sub-agents.

Possible value

  • Retryable integrations and side jobs.
  • Parallel read-only analysis or model/profile evaluation.
  • chat.agent(), sub-agents, and Realtime can stream assistant output and progress to a viewer.

Constraints

  • Cloud workers do not automatically have the Goal Node’s checkout, Boomux daemon, or owner-only bridge sockets.
  • Trigger sessions are not interactive Pi TUI sessions and do not own Omarchestra PTYs.
  • Self-hosting adds webapp/worker operations; its feature table lists checkpoints and autoscaling as unavailable when self-hosted.
  • Task-trigger idempotency does not make external side effects exactly-once.
Best: managed auxiliary workFuture: streamed headless-agent viewer

Inngest

Event-driven durable functions + AgentKit

Durable functions use memoized steps, retries, event waits, concurrency controls, batching, and flow control. Completed step results are reused when the function replays.

Execution placement

  • serve() exposes a function through an app HTTP endpoint.
  • connect() opens an outbound WebSocket from a long-running app worker; no public inbound listener is required.
  • This offers a path to run functions on an Execution Node, but exact per-Goal Node routing is not established by generic worker-pool behavior.

AgentKit and constraints

  • AgentKit provides agents, shared Network state/history, tools, routers, and realtime agent events.
  • Ready-made UI hooks are React-oriented; QML needs a stream/projection adapter.
  • Function replay is not preservation of a Pi process. Cancellation occurs between steps; an active step is allowed to finish.
  • Self-hosting is available, but reliability, upgrades, and recovery become the operator’s responsibility.

04 / Use-case categories

Where an engine could help

Strong
Integrations and background jobs

Webhook-driven GitHub/PR work, notifications, scheduled maintenance, and other asynchronous jobs. The Runner decides whether events change a Goal or Assignment.

Strong
Offline evaluation

Batch model/profile/prompt evaluations against fixed fixtures. Useful in development; an LLM score should not quietly become a live acceptance gate.

Sidecar
Read-only research or triage

Parallel analysis over an immutable Artifact or commit may return supporting evidence. Keep it auxiliary, preserve revision references, and do not let it satisfy a visible Agent’s Assignment.

Strong primitive
External approval waits

Trigger waitpoints or Inngest waitForEvent can wake a job after an external response. The Runner validates the exact Goal, Assignment, Artifact revision, and user intent.

Future mode
Swarm viewer

Stream worker status, selected assistant messages, tool activity, and Board-thread links to a browser or Companion. Keep streams distinct from Board messages; define access and retention.

Poor authority fit
Visible Pi and PTY lifecycle

Keep process identity, terminal persistence, manual takeover, write admission, and gate acceptance in the Runner/bridge/Boomux chain. An engine can request a validated action, not claim that it happened.

05 / Possible Omarchestra options

Future directions—not approved scope

A · Preserve MVP

Use the Node-local Team Runner for visible Pi work. Revisit external engines only for a concrete workload the Runner should not own.

B · Auxiliary-job adapter

Define a narrow Omarchestra-owned port. Pass immutable Artifact/commit references, store platform run IDs as opaque metadata, and let the Runner validate/project results.

C · Explicit swarm mode

Offer platform-managed/headless workers with distinct identities and a high-level viewer. This deliberately extends the current visible-Pi contract; it must not pretend to be the same managed Pi Agent Run.

Design worker locality/sandboxing, source and secret access, assistant/tool-message privacy, stream replay, Board permissions, one-writer admission, gate authority, cancellation, and human control.

D · Streams as projection input

Normalize external events—worker started, assistant delta, tool started/completed, result available—into bounded presentation events. Keep authority-bearing transitions on the Runner protocol; do not give QML platform credentials.

Relative fit: Trigger.dev is attractive for managed, isolated async work. Inngest is especially interesting for an app-owned node-local worker and AgentKit streaming. Neither should become canonical workflow authority without explicit design work.

06 / Evaluation questions

If this becomes actionable

Compare both engines with a small non-production slice. Do not assume worker affinity, exactly-once effects, stream replay, or process cancellation.

  1. Can assistant text, tool events, and run status stream to browser and normalized Companion projection, including reconnect and gaps?
  2. Can a run be proven to execute on the exact Goal-owning Node when multiple Nodes are online or one disconnects? For Connect, do not infer affinity from worker IDs or concurrency.
  3. Can a crash around a side effect duplicate Board messages, Assignment delivery, gate execution, or Artifacts?
  4. How do deployment/replay changes interact with frozen Team Profile and gate contracts?
  5. Can approval and stop requests be validated by Runner without broader bearer-token authority?
  6. What content reaches platform traces, model providers, and durable history? Can privacy and retention policy be enforced?
  7. What are the real install, upgrade, backup, recovery, and support costs on local and remote Nodes?

Research checklist only—not an approved spike or authorization for live-system tests.
