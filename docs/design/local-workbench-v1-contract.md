# Local Workbench v1 contract

Status: Phase 0 technical decisions. Runtime behavior below is specified, not implemented by this document. Phase 1 implements only an injected presentation shell.

Authority: [slice plan](../plans/local-workbench-v1.md), [coordination amendment](agent-coordination.md), [MVP](mvp.md), [domain language](../../CONTEXT.md), [terminal behavior](pi-terminal-behavior.md), ADRs [0001](../adr/0001-install-a-persistent-omarchy-companion-plugin.md), [0002](../adr/0002-observe-ordinary-pi-before-explicit-adoption.md), [0003](../adr/0003-use-connection-bound-observer-capabilities.md), [0004](../adr/0004-explicit-purge-of-terminal-retired-history.md). Operational transitions and failure windows are in [the transition tables](local-workbench-v1-transitions.md).

## C1. Code, deployment, and authority

**Decision:** `packages/local-workbench-v1/` is a new private TypeScript ESM package with production-intended protocol/presentation code. It imports no runtime code from `prototypes/` or `spikes/`. Reuse means explicit redesign against their evidence, not promotion. Existing prototype code and release bytes remain untouched. Phase 2 must select reviewed extraction/reimplementation into one runner composition, not run a prototype registry alongside another management service. One local runner owns every Project's store, admission, gates, and projections. No Fusion runtime dependency, PTY ownership, scheduler, Board backend, or service daemon is added here.

Phase 1 supports Node 22.6+ with explicit strip-types flag where required, on local GNU/Linux. Tests record the actual version, not a claim that every newer version was tested. SQLite requires the Node SQLite API and its version-dependent flag in Phase 2. The compatibility target for eventual installed presentation is Omarchy 4.0.3-1 / Quickshell 0.3.1-1. Unknown installed compatibility blocks setup/runtime negotiation rather than mutating configuration. Pi 0.84.4 is the existing bridge evidence baseline, not certification of the currently installed Pi. Phase 1 uses no Pi API. Before a future bridge implementation, read installed extension documentation fully and validate its exact capabilities with bounded injected tests. Cancellation remains unsupported unless that adapter advertises and tests it.

Package Companion 0.6.0. The archived retirement ledger reserves 0.5.0 metadata even though the materialized historical catalog contains only 0.2.0/0.3.0/0.4.0. Respect that reservation. The later recorded host target is Omarchy 4.0.3-1, superseding the original 4.0.2-1 packaging baseline for this new release only. Neither selection claims installation or live compatibility validation. Preserve the existing plugin identity and immutable old assets/defaults. The new package contains only its new release, not a copied competing historical catalog. An explicit future setup planner selects it.

Retained baseline and additive packaging. Before the Phase 1b task-first redesign edits any QML, the exact pre-redesign 0.6.0 assets are frozen under `companion/retained/0.6.0/` with recorded SHA-256 digests, including the manual installation forwarder (`AgentConsole.qml`) that the historical installer's panel entry point requires. Retained releases are outside the active production catalogue: `companion/releases.ts` builds the one active release from the mutable plugin source and must not be built from retained bytes, while `companion/retained-releases.ts` exists only for reproducibility, tests and receipt-backed restore. The redesign publishes additively as 0.7.0 with the same plugin ID; 0.6.0 remains byte-reproducible. `test/retained-release.test.mjs` re-verifies the retained digests.

Future command contract, **not shipped commands**: `omarchestra setup --plan --release VERSION` is read-only; `omarchestra setup --apply PLAN_ID --authorize DIGEST` validates exact ownership, compatibility, configuration preconditions and assets before mutation. `omarchestra workbench start` opens the one foreground durable runner, `omarchestra workbench open` negotiates the already-installed Companion, and `omarchestra workbench hide` closes only presentation. Missing installation produces an actionable error, never automatic setup. No global Pi configuration, user service installation, terminal launch, or shell reload occurs during start/open/hide/stop. Phase 1's executable path is the injected package harness and its automated gate, not these future commands.

## C2. Project, context, and writer admission

`Project = {projectId, executionNodeId, canonicalPath, gitCommonDir, revision}`. IDs are random opaque values, never paths. Identity is `(executionNodeId, canonicalPath)`. Registration resolves symlinks to a canonical absolute Git top-level path on the selected local Node. Reject missing/non-Git/bare paths, inaccessible paths, nested selection that does not explicitly resolve to the confirmed top level, and unsupported linked-worktree/submodule execution. This slice does not create worktrees. A repository with no HEAD is registrable but not execution-ready. Repository replacement or changed Git common-directory binding requires fresh confirmation.

Registration does not inspect or adopt Pi based on cwd. Start includes an explicitly confirmed execution-context tuple `{projectId, executionNodeId, canonicalPath, gitCommonDir, headOid, baselineDigest}`. The exact current Run must independently report matching context; mismatch blocks rather than changing Pi cwd. No cwd/PID/title-derived Adoption authority.

Dirty checkout is allowed with **explicit start confirmation of the recorded dirty baseline**, not silent cleaning or a blanket clean-only restriction. Include tracked modifications and all untracked/ignored files in the bounded content fingerprint below. The confirmation explains that existing changes are retained and there is no isolation. Changed baseline requires reconfirmation. Unsupported or excessive fingerprint scope blocks execution, not Project navigation.

One active Assignment per Project and at most one write-authorized Assignment are admitted in the same synchronous transaction as attempt creation. Roles do not grant a lease. `Writer = {projectId, assignmentId, attemptId, epoch, state: held|uncertain}`. Admission checks expected Project revision, Run readiness/control, context, no other active Assignment, and no held/uncertain prior writer. Lease expiry, disconnect, retirement, purge, stop ACK, idle report, or replacement never clears uncertainty. Completion can release only after stable candidate validation and confirmed quiescence under C9. Otherwise retain `uncertain` even when an Assignment is terminal. Explicit operator reconciliation records prior effects and an acknowledgement of unmanaged interference risk. If tools may still be running or evidence is missing, conflicting dispatch stays blocked. This is orchestration admission, not OS write isolation.

## C3. Persistence, ownership, backup, retention

Future default: `$XDG_STATE_HOME/omarchestra/workbench/` or `~/.local/state/omarchestra/workbench/`, canonicalized outside every registered Git Project. Owner-only directories 0700 and files 0600. Database `workbench.sqlite`; local transport under owner-only `$XDG_RUNTIME_DIR/omarchestra/`. Reject foreign ownership, symlink substitution, unexpected files at owned targets, or insecure parents. Automation injects disposable roots and never resolves these defaults.

SQLite store schema version 6 and independent fence schema version 2 (older development store schemas are refused; no migration or restore is enabled), foreign keys ON, rollback journal DELETE, synchronous FULL, `BEGIN IMMEDIATE` for authority transactions, busy timeout 1000 ms. One lifetime exclusive owner lock is required in addition to SQLite transaction locks. Acquire a SQLite exclusive transaction on a separate `owner.sqlite` connection for the runner lifetime; keep that database rollback-journal mode. A second runner fails closed while the lock is held. OS resource release after crash releases the lock, but ownership evidence still must match before opening history. Do not use PID or stale lock-file deletion as takeover authorization. Durable node identity, ownership manifest, schema/version, epoch, identity fences and resource paths are verified before accepting frames.

Current partial Phase 2 implementation records exact local parent/resource identities in `ownership.json`, validates them before opening retained SQLite resources and rechecks them on store/ledger access. Roots without that receipt are refused rather than silently adopted. Backup retention uses `backups/inventory.json` with file identity/hash records and read-only SQLite verification. These receipts are not portable restore authorization. See the [persistence repair checkpoint](../reviews/local-workbench-phase-2-verification/persistence-checkpoint.md) for implemented bounds and remaining S1 work; Phase 2 remains blocked.

The S1 schema separates immutable `(Node, process capability, Pi-session capability, extension capability)` identity plus Goal association from committed `(Goal, Role, Run)` membership; proposals do not populate the membership table. Connection/readiness remains separate from durable membership. Vacancy high-water marks use `(Project, Goal, Role)`. Only the challenged bridge can establish the identity facts; persisting caller-supplied fields is not same-process proof. The existing legacy Adoption/projection path must be converted to these tables in S4/S5 before management acceptance.

Retirement commits independent revocation intent before the store retirement/membership-release transaction. Purge commits an irreversible ledger intent, then atomically removes leaf binding/identity/membership and associated Adoption/retirement events while preserving unresolved Project effect evidence; finally it compacts ledger history into only Run replay ID and exact-incarnation hash. Recovery completes interrupted operations before admission. No pair of writes across the databases is described as atomic. Vacancy and event-cursor high-water marks survive deletion. A failed cross-ledger operation latches admission unavailable until reopen/reconciliation. See the [S1 binding/fence checkpoint](../reviews/local-workbench-phase-2-verification/binding-fence-checkpoint.md).

The [first S2 command checkpoint](../reviews/local-workbench-phase-2-verification/command-transactions-checkpoint.md) now commits durable Project/Goal/check/selection effects, event/revision and normalized outcome receipts together. Nested store work uses savepoints; private staged counters are published only after the command transaction commits. Store schema 3 introduced outcome reason/detail retention for replay. Schema 4 adds a durable management-operation journal: [retirement/purge outcomes](../reviews/local-workbench-phase-2-verification/management-outcomes-checkpoint.md) now reconcile prepared authorization, independent revocation and final event/receipt before admission or acknowledgement. Request-Adoption and Take control also commit their no-send effects and receipts together. Schema 5 adds [durable management delivery intent](../reviews/local-workbench-phase-2-verification/delivery-outbox-checkpoint.md): authorization effect/event/outcome and queued frame commit together; binding commitment likewise records its queued frame atomically. Only post-commit callbacks may attempt those writes on the captured live subscription. Attempts are marked before calling the port; throwing writes are unknown, local returns are written (not Pi receipt). Reopen marks queued records not-sent and unfinished attempts unknown without replay. Purge removes their frame bodies with Run history. Source publication/reconnect and complete command-envelope validation are covered under C4. Schema 6 binds receipts and management journals to the full original envelope fingerprint. Real bridge/challenged management remain incomplete.

All commit-dependent state/event/outbox changes share one transaction. Increment a durable runner epoch at startup. Before dispatch, mark any unfinished delivery/gate/writer state uncertain and reconstruct identity fences. Clean shutdown closes connections and files without deleting history. Console hide/reload never touches the database.

Migrations are explicit forward-only transactional steps after exclusive ownership and a verified SQLite backup. Retain two clean backups with hashes and schema metadata outside Git, owner-only. No automatic downgrade, overwrite of drift, deletion of unknown runtime directories, or automatic backup restore. Integrity/schema failure starts no dispatch and reports the exact recovery action. Explicit restore first preserves the damaged database, verifies backup integrity, creates a new epoch, and treats restored in-flight work as uncertain. Never revive revoked bindings from an older backup: recovery requires the latest independently retained fence ledger; if unavailable, all pre-restore bindings are blocked and operator intervention is required. A future implementation must atomically/recoverably maintain that ledger before enabling purge or restore.

Project/Goal/Assignment records, accepted evidence, and explicit managed content are retained by default, not automatically expired. Terminal retired-Run purge is separately confirmed and leaf-only under ADR 0004. It does not delete Assignment results, external artifacts, Pi files, or checkout data. Minimal exact-binding fences and vacancy-generation high-water marks survive purge and backups. Event transport replay keeps the newest 10,000 events; older result records remain queryable by bounded navigation, and missing event history produces an explicit gap. No new generic history-delete feature is introduced.

## C4. Protocol, projection, intents, and feedback

Protocol identifier `omarchestra.workbench/v1`. Phase 1 uses injected calls. Future local wire representation is UTF-8 NDJSON over owner-only Unix sockets. No public listener or remote execution in this slice. Unknown fields, invalid enum values, unsafe numbers, wrong protocol, and bounds violations reject the whole envelope before mutation.

Common limits: random opaque IDs are 1–128 ASCII letters/digits/underscore/hyphen; revisions/cursors are nonnegative safe integers; maximum encoded envelope 256 KiB; depth 8; at most 64 keys/object; ordinary display strings 512 UTF-8 bytes; maximum 100 records per page/collection. Oversized collections require runner pagination, never silent dropping of authority-bearing records. Node/Project/Goal/Run IDs are distinct typed fields, not interchangeable equal strings.

```
Snapshot = {protocol, sessionId, pluginGeneration, runnerEpoch, revision,
  cursor, connection, projects, goals, selectedProjectId, selectedGoalId,
  managedAgents, observedSessions, retiredRuns, assignments, activity,
  capabilities, actions}
Event = {protocol, sessionId, runnerEpoch, eventId, cursor,
  baseRevision, revision, kind, payload}
Intent = {protocol, sessionId, pluginGeneration, runnerEpoch, intentId,
  expectedRevision, kind, target, payload}
Feedback = {intentId, sessionId, target, originRevision,
  status, reasonCode, committedRevision}
```

Phase 1 accepts only empty `projection_update` and `agent_connected` event payloads as presentation revision notifications. Any data-bearing event requires a full authoritative replacement snapshot and is rejected otherwise, so state changes are never silently discarded. The package's exact schema is in `packages/local-workbench-v1/console/schema.ts`. Runtime intent payloads remain unavailable where the shell cannot represent the full confirmation contract. Collections may use explicit page descriptors in a later implementation schema. Payloads are discriminated closed unions, never arbitrary JSON passed to QML. `target` binds every relevant Project/Goal/Run/observed session and, for replacement, predecessor and vacancy generation. The phase implementation must record its exact concrete schema alongside executable validators. `connection` separates loading/connected/stale/reconnecting/gap/error; it never fabricates agent connection. Unknown metadata is null/unavailable. Agent cards separately carry membership, control, connection, Assignment state and a runner-committed role/control display value. Original/replacement cards have the same schema, with optional predecessor linkage. Actions contain `{kind, target, enabled, reasonCode, reason}`. The runner computes domain eligibility. The adapter may only narrow availability for stale/unsupported/invalid presentation, never grant it.

New Projection Sessions begin with a full snapshot. Events must advance cursor by exactly one and match baseRevision/current epoch. Exact duplicates are ignored; same cursor/ID with different payload rejects and forces resnapshot. Gaps, regression, epoch changes and publication failures latch stale state until a fresh validated snapshot. No merging old identity into a new snapshot. Last-known values stay visibly labeled. Local monotonic heartbeat every 1 second, stale after 2 seconds without authoritative update. Sender wall clocks do not authorize liveness. Snapshot updates may replace full collections atomically instead of implementing arbitrary patches.

At most 16 pending intents per presentation session. Adapter assigns an opaque intentId and captures current target/session/revision when emitting a confirmed action. QML emits plain user payloads and never manufactures durable revisions, cursors, readiness, or writer admission. Feedback lifecycle is `submitted → acknowledged|rejected|unknown|stale|expired`. `acknowledged` means the runner committed that intent, not that Pi delivery or cancellation succeeded. Show downstream phases separately. ACK deadline 5 seconds gives `unknown`, not retry success. Query outcome by the same intentId on reconnect; do not submit a fresh authority action automatically. Durable runner dedup stores the canonical complete-envelope hash and result for the retained record lifetime. Same ID and original envelope return the prior result; changed metadata or payload under that ID rejects. An exact historical replay is result lookup, never fresh authority. A dedup tombstone can remain after selective history purge without reconstructing a Run card.

The [S2 source checkpoint](../reviews/local-workbench-phase-2-verification/source-outcomes-checkpoint.md) implements staged outcome → successfully displayed snapshot → final feedback in the injected runner/source/adapter path. Same-owner reconnect queries unresolved original intents without re-executing them. Queries supply the complete validated original intent and match its complete-envelope fingerprint and original session against the retained receipt. A known original-command result is not a renewed confirmation or authority action. Fresh adapter instances use independent opaque intent namespaces. Owner-driven one-second snapshot heartbeats, forced resnapshot and exact subscriber disposal are implemented; native entry and Pi delivery remain separate unfinished contracts.

The [S2 authority-envelope checkpoint](../reviews/local-workbench-phase-2-verification/intent-envelope-checkpoint.md) validates the full closed protocol/identity/counter/payload shape and management target association before deduplication or routing, using a private bounded JSON-data copy without invoking user hooks. Malformed envelopes are rejected without receipts; valid stale requests retain their original submitting session. Inspection-cache changes roll back with failed receipt persistence. Direct callers cannot bypass the presentation validators or alter a routed command after fingerprinting. This is not Pi identity proof or native transport acceptance.

Authority confirmations expire after 30 seconds and are invalidated by session/generation/epoch/target identity or relevant revision changes. Form drafts survive ordinary projection updates and are keyed by Project/Goal/Run as applicable. Draft text may remain when authority changes, but it is never an active confirmation. Clear obsolete feedback on target/session changes and reject late feedback for an obsolete association. Escape cancels a confirmation without emitting an intent. Board is visible but disabled, emits no action, and has no simulated messages. Fixture mode is persistently labeled, and unsupported management/execution actions cannot pretend to be live.

## C5. Assignment delivery and exact acknowledgement

`Assignment = {assignmentId, projectId, goalId, agentRunId, goalText, writeAuthority, state, revision}`. `Attempt = {attemptId, assignmentId, ordinal, runBinding, gateVersion, context, writerEpoch, controlEpoch, deliveryId, state}`. Binding includes Node/process/session/extension capabilities and exact challenged connection, not only Run ID. Original and replacement Runs follow one dispatch resolver and identical checks.

One explicit start confirmation creates Assignment/attempt/admission/outbox records atomically. The delivery port may call same-process `pi.sendUserMessage()` only after commit, fresh readiness, and final identity/control/context/admission checks. No observation or Adoption path dispatches an Assignment. The surviving extension remembers `(assignmentId, attemptId, deliveryId, payloadDigest)` and responds `accepted`, `busy`, `duplicate`, or `invalid`. Accepted means the same Pi API accepted input, not completion. Duplicate must include the stored receipt/state and may not create another turn. Busy refuses without queueing, invalid refuses without mutation. ACK deadline 5 seconds creates delivery uncertainty.

The write-ahead outbox cannot provide exactly-once execution: crash after send but before receipt persistence is `delivery_unknown`. Query the surviving challenged extension for its receipt. No automatic resend, even with a new delivery ID. An unprovable outcome requires explicit reconciliation. Extension reload, Pi restart, changed session, and reboot do not inherit dedup identity. Extension-originated input is excluded from human takeover; interactive source causes durable takeover without reading content. Slash/user-bash coverage retains the accepted best-effort R1 limitation, so users must use Take control where automatic detection is unavailable.

## C6. Completion signal and artifacts

Only the exact current managed binding may submit `Candidate = {candidateId, assignmentId, attemptId, agentRunId, controlEpoch, summary, artifactRefs}` through a dedicated structured submission port. Maximum one pending candidate per attempt, 16 references and 8192-byte summary. Stable duplicate submission is idempotent; conflicting reuse rejects. `agent_settled`, quiet tools, conversational “done”, or an artifact appearing on disk is not submission or acceptance.

Artifact references are relative Project paths with no `..`, absolute path, URI, NUL, or symlink traversal. At most 4096 bytes/path. Resolve under the confirmed Project and associate a content hash, length and media kind. In-scope regular files only, maximum 16 MiB each. References do not authorize reading Pi session history or automatic rendering of file bodies. Missing/escaped/changed artifacts reject candidate validation. User selection of an artifact is explicit content, not permission to mirror a transcript.

## C7. Gate authority and versioning

`Gate = {gateId, version, digest, executable, argv, cwd, env, resources, timeoutMs, outputBytes, semanticClaim}`. Operator confirms this definition before attempt admission. Only an operator intent can edit it. Role, worker messages, artifacts, or scripts cannot alter this authority. Store canonical definition bytes and SHA-256 digest outside the checkout. Freeze the entire definition and validator resources per attempt. Version changes invalidate pending results and require a newly confirmed attempt, not relabeling old evidence. Gate changes do not evade configured attempt/time limits. Optional Reviewer participation carries no veto or lease.

Executable and every declared script/config/lockfile dependency are explicitly enumerated and hashed before confirmation. Copy bounded validator scripts/configuration into runner-owned validator resources where their execution semantics permit. Otherwise pin the checkout resource hash and verify before and after execution. Worker edits to a referenced resource yield `gate_changed`, never success. Dynamic undeclared validator dependencies make reproducibility unavailable and block acceptance until the operator defines a bounded resource closure. Hash pinning is not adversarial sandboxing: same-UID malicious code can bypass permission conventions. The threat model is trusted local operator/tools with accidental or unauthorized contract drift detected, not hostile-worker OS confinement.

## C8. Gate execution

Explicit absolute executable and argv array, maximum 64 arguments, each at most 4096 bytes, total 32 KiB. No shell string, expansion, eval, or worker text interpolation. Canonical cwd is the confirmed Project root. Validate executable/resource hashes immediately before spawn. Gate invocation is code execution and requires the operator's start confirmation, never a preview action.

Environment is constructed, not inherited: fixed `LANG=C.UTF-8`, `LC_ALL=C.UTF-8`, scratch HOME/TMPDIR, and explicit operator-confirmed nonsecret entries (at most 32 keys, 4096 bytes/value). Executable resolution is absolute; an optional fixed PATH for validator child tools must be shown in the frozen definition. Do not load dotenv, provider credentials, SSH agent, Pi configuration, or ambient package hooks implicitly. Default timeout 60,000 ms, configured range 100–300,000 ms. Capture stdout/stderr separately, maximum 32 KiB each, 64 KiB combined; exceeding the bound is `output_limit`, not pass. Diagnostics remain restricted under C13.

Runner owns one validator child and disposable scratch directory per gate. Normal exit 0 is only a provisional pass subject to C9 and intervention fences. Nonzero exit, spawn error, timeout, output limit or unavailable exit status is non-pass. On timeout/stop, request cooperative termination of the validator child only; do not signal Pi or its tools. No kill escalation is introduced. If validator termination/descendant quiescence cannot be established, retain writer uncertainty and quarantine its scratch resources instead of unsafe cleanup. Validators that detach persistent processes are unsupported. A gate timeout may therefore require attention rather than immediate retry.

## C9. Candidate association and validator mutation

The runner, not the worker, computes a deterministic manifest containing canonical Project/context identity, HEAD/index digest, sorted relative paths, file type/mode and SHA-256 content digest for every working-tree file, including dirty, untracked and ignored files. Exclude only Git administrative storage from the file walk, but include HEAD/index/config state in the context fingerprint. Symlinks are represented by link bytes and rejected as artifact/validator traversal targets. Reject special files, unreadable paths, nested Git/worktree ambiguity, more than 100,000 files, individual files above 64 MiB or more than 1 GiB total hashing. Fingerprints are evidence, not copied repository content in the store/QML. A double scan must agree before gate launch.

Candidate record persists the pre-gate manifest digest, artifact hashes, frozen gate digest, attempt/Run/writer/control epochs and revision. No new managed write occurs while validating. Compute a second stable manifest after gate exit. Any change, including a validator-created ignored output, yields `candidate_changed`, even if exit is zero. A mutating validator may produce artifacts, but cannot accept that invocation. The operator must configure a nonmutating gate or explicitly submit the new candidate for another eligible attempt within limits. Do not exclude convenient output directories to manufacture a pass.

Stable pre/post scans detect observed drift, not transient writes restored between scans. Accepted evidence explicitly states this limitation and does not claim filesystem isolation. Unmanaged interference remains possible. Acceptance transaction rechecks current fingerprint, gate resources, current epochs, no stop/takeover/reconciliation, candidate identity and quiescence. Known active tools, stale lifecycle facts, missing cancellation evidence or changed context yield attention/uncertain, not acceptance. No result for a predecessor, old attempt, stopped epoch, or pre-takeover candidate may complete current work.

Additional bounded execution decisions: manifests use UTF-8 canonical JSON arrays of sorted `[path,type,mode,length,sha256]` entries, prefixed by the literal domain `omarchestra.candidate/v1` before SHA-256. Paths are at most 4096 UTF-8 bytes. A complete double scan has a 60-second deadline. Maximum aggregate referenced artifact bytes is 256 MiB, validator resources 64 entries/64 MiB, and scratch usage 256 MiB. Exceeding any bound is nonaccepting attention. Detached descendants are unsupported, not a new process supervision feature. A validator that cannot establish its own synchronous resource closure is ineligible.

`QuiescenceEvidence = {binding, attemptId, controlEpoch, source, status, sequence, runnerReceivedAt}` where status is `confirmed|active|unknown` and source is `surviving_bridge_and_operator_reconciliation|validator_exit`. Runner monotonic freshness is at most 2 seconds at admission/acceptance. For Pi work, confirmed requires an exact challenged surviving bridge reporting no known model/tool work plus the operator's explicit reconciliation of possible unobserved effects whenever coverage was lost or manual work occurred. Validator exit proves only that validator child exited, not Pi tools or descendants. An idle report alone is never confirmed quiescence. Unavailable source, known active work, unsupported descendant behavior, or unobserved interval without reconciliation yields unknown and retains the writer. This is an auditable orchestration assertion under the accepted best-effort activity limitation, not OS proof of checkout safety.

## C10. Retry, limits, and Goal aggregation

Start confirmation includes `Limits = {maxCorrections, elapsedMs}` with maxCorrections integer 0–3 (default 1), elapsedMs 1000–3,600,000 (default 900,000). At most 1 + maxCorrections dispatched attempts for this Assignment, including operator retries. Persist attempt count and elapsed accounting. Runtime monotonic time measures the current epoch; restart with an unprovable elapsed interval blocks automatic continuation rather than granting a fresh budget. No inferred token/cost budget, watchdog agent, or arbitrary limit expression in v1.

On ordinary gate failure, correction payload contains original goal reference, same frozen gate/version, candidate/attempt IDs, reason code, permitted bounded diagnostics and artifact references. Retry only with current managed/readiness/context, quiescent prior attempt, admission, remaining limits and no stop/takeover. Error/timeout/changed evidence first requires explicit attention and safe reconciliation, not blind repeated execution. No mandatory Reviewer. A valid pass atomically accepts the Assignment and completes its one-Assignment Goal with exact gate/candidate/result references. The UI says which executable gate passed, never semantic verification for an artifact-presence gate.

## C11. Takeover and return

`Handoff = {handoffId, assignmentId, attemptId, agentRunId, controlEpoch, claimedState, summary, artifactRefs, outstandingEffects}`. Same content bounds as Candidate; claimedState is `candidate|partial|blocked`, outstandingEffects is `none_reported|may_be_active|unknown`. Claims do not prove tools ended. Store the structured handoff durably, not conversation text.

Take control and source-only interactive takeover atomically increment controlEpoch, set manual_takeover, mark affected work needs_reconciliation, and pause automatic Assignment/message delivery. Already running tools may continue. Return to team is an explicit acknowledged request for one structured handoff from the same Pi, only at a supported delivery boundary; busy/unknown remains paused. Timeout 30 seconds is attention, not managed reset. Receipt enters reconciling. `accept` requests candidate validation under the frozen gate and current writer checks; it is not direct acceptance. `resume` or `retry` requires explicit current-revision intent, handoff, context/admission and stopping-limit checks. Record reconciliation before managed dispatch and create a fresh control epoch. Gate results arriving during takeover remain historical, nonaccepting evidence. Original/replacement paths share this schema and resolver.

## C12. Stop, retirement, recovery

Stop triggers are `operator`, `elapsed_limit`, `attempt_limit`, `protocol_uncertainty`, or `gate_failure_attention`. Persist `{stopId, trigger, assignmentId, revision, dispatchRevoked, cancellationStatus}`. Revoke new dispatch and automatic message delivery atomically first. Cancellation status is independently `not_requested|requested|acknowledged|unsupported|timeout|unknown`; request only a tested advertised cooperative API, with 5-second ACK deadline. ACK does not prove tool/process termination. Never kill Pi, close ordinary terminals, roll back files or automatically resume stopped work. Already received gate pass cannot complete after stop wins its transaction.

Disconnect/lease expiry revokes readiness, not membership or writer uncertainty. Recovery before retirement requires the exact surviving Node/process/session/extension capabilities, fresh connection challenge, retained commitment and source-only pending takeover reconciliation before readiness. Original and replacement commitments resolve through one logical Run interface regardless of storage tables. Readiness follows committed binding delivery and exact receipt. Never register a retained replacement as Unassigned.

Retire only a disconnected/exited current Run with exact revision confirmation. Atomically fence binding, release Role occupancy, retain writer uncertainty and increment vacancy generation. Replacement is fresh acknowledged Adoption with predecessor and vacancy generation, never automatic Assignment transfer. Purge only a terminal retired leaf and retain minimal binding fence plus generation high-water mark. Late ACK/readiness/result/recovery/takeover frames for retired/purged bindings reject before mutation, including registration under a new observed ID. No re-Adoption of the retired surviving incarnation in this slice. No Pi/session reload or reboot recovery guarantee.

## C13. Managed content and privacy

Observation remains lifecycle-only with all existing exclusions: no prompts, responses, thinking, tool arguments/results, terminal output, repository contents, credentials or environment values. Takeover reads source only. Explicit Goal/Assignment/handoff/candidate text has separate operator-authored/explicit-submission provenance, maximum 8192 UTF-8 bytes per field, retained owner-only with its durable record. Treat display strings as plain text, never markup, command text or QML source. Reject control characters except tab/newline in multiline fields. General activity contains stable reason codes, IDs, bounded labels and state transitions only, never submitted text or validator stdout/stderr.

Project/Goal detail may display explicitly supplied goal/summary text. Artifact bodies are not automatically projected. Gate diagnostics are restricted owner-only evidence by default and absent from general snapshots. An explicit operator request may project a filtered detail excerpt up to 4096 bytes, stripping terminal escapes/control characters and known credential patterns. The UI warns that filtering cannot guarantee secret removal. Secret-bearing executable environments are unsupported in this bounded contract. No request collects Pi conversations to improve filtering. Content limits reject input visibly rather than silently truncating the acceptance definition; diagnostics may be truncated with an explicit marker. Retention follows C3, not a transient console cache.

## C14. Project-scoped configured acceptance checks

**Decision:** A Project may hold a bounded catalogue of reusable acceptance-check definitions. The catalogue is Project-scoped, injected and presented in this slice; it is not a durable preset service. No repository script discovery, shell-string parsing, template marketplace, second store or ambient configuration lookup is introduced. A check selection is a reference, never execution authority.

`CheckDefinition` is the runner-owned full definition and reuses the C7 gate fields exactly:

```
CheckDefinition = {checkId, version, digest, name, summary, mode, semanticClaim,
  executable, argv, cwd, environment, resources, timeoutMs, outputBytes}
```

- `checkId` is an opaque 1–128 ASCII letters/digits/underscore/hyphen value; `version` is a nonnegative safe integer; `digest` is the lowercase SHA-256 hex of the canonical definition bytes stored outside the checkout. Identity is `(projectId, checkId, version, digest)`.
- `mode` is `validator` or `artifact_presence` (display only). `semanticClaim` states what a pass proves, so the UI never claims semantic verification for an artifact-presence check.
- `executable`, `argv`, `cwd`, `environment`, `resources`, `timeoutMs` and `outputBytes` obey the C7/C8 bounds (absolute executable, ≤64 argv entries, constructed environment, declared and hashed resources, 100–300,000 ms, bounded output).

Presentation summary `CheckSummary = {checkId, version, digest, name, summary, mode, commandSummary}`. The general snapshot projects `checks: CheckSummary[]` (at most 100) plus the current Assignment draft's `selectedCheckId`/`selectedCheckVersion`. Full definition bodies are not general snapshot content; they appear only in an explicit detail/expansion under C13.

**Selection.** An Assignment preparation carries only `{checkId, version}`. The adapter validates explicit allow-listed fields for the selection intent and for `start_assignment` (`checkId`, `checkVersion`); payloads stay discriminated closed unions, never arbitrary JSON.

**Edit authority.** Only an operator intent (`configure_checks`) may create or change a definition. Roles, worker messages, artifacts and scripts cannot alter this authority. The configuration destination edits structured draft data, not a shell command string. Saving does not execute anything. The validated payload is `{projectId, checkId, checkVersion, name, summary, mode, commandSummary, definitionDraft}`. `definitionDraft = {executable, argv, cwd, environment, resourcePaths, timeoutMs, outputBytes, maxCorrections, elapsedMs}` carries explicit absolute paths, argument arrays and nonsecret environment entries under C8/C10 bounds. It contains no caller-authored hashes or readiness/authority fields. The adapter rejects an unknown selected Project, target or check version; the future runner owns persistence, version advancement, canonical resolution and hashing. Command summary is display-only and never executable input. The Advanced definition editor is separate from Goal creation and collapsed initially.

**Resolution and freezing.** At start review the runner resolves the reference to the full definition, verifies the digest against the stored canonical bytes, and freezes the entire definition and its validator resources per attempt under C7. The start detail carries the resolved facts. If the reference cannot be resolved, or the digest differs, start is blocked with `check_unavailable`/`check_changed`; a version change invalidates pending results and requires a newly confirmed attempt, never relabeled old evidence.

**Invalidation.** Changing the selected Project, selected Goal, target agent, `checkId`/`checkVersion`, session/generation/epoch or relevant revision invalidates the pending start review and any confirmation, without deleting unrelated draft text (C4). Any changed full snapshot, including a same-revision check digest/availability/detail replacement, conservatively invalidates captured reviews. Exact start details must match Project, Goal, agent, check version/digest and captured task text; a mismatched fixture proposal is unavailable, not silently rebound. Draft text keyed by target survives.

**Empty and error states.** No configured check: Assignment preparation shows the `Configure checks` path and start is disabled with `check_not_configured`. Unknown or stale version: disabled with `check_changed`/`check_unavailable`. Catalogue load failure: checks are unavailable, start is disabled, the reason is shown, and no definition is fabricated.

**Unavailable execution.** A fixture catalogue entry, a selection, a preview configuration or a staged snapshot never grants authority or executes anything. Phase 1 implements only this injected presentation contract and its strict validators; the durable runner persists and resolves the catalogue under C7/C8 in Phase 2, and executable gate authority remains Phase 3/4.

## Phase 1 concrete detail and draft boundary

The optional snapshot `details` collection is a closed discriminated union in `console/detail-schema.ts`: `adoption`, `start`, `handoff`, `stop`, `diagnostics`, and `check_configuration`. The last is `{kind, projectId, checkId, checkVersion, definitionDraft}` for explicitly supplied configuration detail; the draft is validated by `validateCheckDraft` and never a frozen execution definition. The start view includes exact Project/Goal/Run/context/baseline plus frozen gate executable/argv/environment/resource digests and limits. Details are still bounded by the common envelope/depth/collection checks. Explicit managed goal/summary text permits 8192 UTF-8 bytes; ordinary labels remain 512 bytes. Diagnostic notices carry state/reason only, never an excerpt in general snapshots.

Phase 1 renders exact confirmation and consent facts but does not emit unavailable start, Adoption-authorization or diagnostic-access requests: `Confirm start`, `Authorize adoption` and diagnostic access stay visibly disabled with a reason and emit nothing. There is no review-only dialog that imitates a committed operation. Create Goal and Save check emit a single validated intent without a redundant confirmation dialog; they do not launch/adopt/dispatch or execute anything. Consequential interventions retain a confirmation dialog with action-specific consequences and inspectable exact target. It emits nothing when no confirmation is pending. The later runtime port must validate the complete immutable proposal and its target/revision before enabling submission.

Drafts are ephemeral text, keyed by Project/Goal/selected Run, retained by the root view and synchronized with the adapter. The Phase 1b task-first destinations and their exact draft keys (`goal:new:<projectId>`, `assignment:<projectId>:<goalId>:<agentRunId>`, `checks:<projectId>:<checkId>`) are specified in the [screen and flow design](local-workbench-v1-screens.md). Limit: 64 target drafts, keys at most 512 characters and serialized draft text at most 24,000 characters each; capacity errors are visible. Ordinary view close/reopen retains them; presentation-process restart does not promise draft recovery. They never preserve authority confirmation. A changed projection or a local two-second presentation watchdog invalidates confirmation and queued actions.

See the [Phase 1 engineering closeout](local-workbench-v1-phase-1-closeout.md) for actual Qt/VM coverage and the remaining native operator checkpoint. Offscreen tests substitute only host/theme/decorative ports; runtime contracts C2–C3/C5–C12 are still specifications, not implementation evidence.

## Closure and implementation boundary

C1–C13 select technical defaults within the approved local slice. There is no known user-policy blocker to Phase 1. Any later request for clean-only admission, secret-bearing validators, automatic uncertain-writer release, transcript collection, mandatory Reviewer veto, or broader recovery needs an explicit policy decision rather than an implementation shortcut.

Phase 1 must implement strict concrete presentation schemas, fixtures and rejection tests against these contracts. It must not claim that fixture transitions enforce a durable writer, run a validator, recover a process or complete a real Goal. Phase 2 covers durable Project/Goal and existing management integration only. Phase 3/4 own executable dispatch/gate/intervention enforcement and must prove the corresponding failure windows before enabling them.

## Phase 2 amendment — durable management, adoption and the refusal boundary

Phase 2 must preserve C1–C14. The implementation below is partial and does not yet enforce every claim in this task-level amendment. The [canonical integration result](local-workbench-v1-phase-2-integration-result.md) records the failing acceptance status and remaining requirements. This amendment cannot weaken C1–C14.

**A1. One durable authority.** The foreground runner owns the Project registry, Team Goals, the check catalogue, the adoption bindings, the projection revision and the event cursor. `console/live-projection-adapter.ts` and the QML layer stay presentation: they validate, render and emit. They never compute Git facts, versions, digests or durability, and the QML never reads Git. `contextMatch` on a Project summary is `false` in Phase 2 because no Run has verified that Project's execution context. It means "no Run has verified", never "is selected".

**A2. Two new intents and one completed one.**

| Intent | Payload | Effect |
| --- | --- | --- |
| `inspect_project` | `{path}` | Read-only Git inspection of one absolute local path. Transient, non-durable, commits no revision, writes nothing. Its outcome is a `registration` detail carrying the exact refusal and readiness reasons. |
| `confirm_register_project` | `{registrationId}` | Re-derives the Git facts for the inspected path and commits one `project_registered` event, selecting the new Project. |
| `create_check` | `{projectId, name, summary, mode, commandSummary, definitionDraft}` | Validated per C14, persisted at version 1 with the digest of the canonical definition bytes. |
| `configure_checks` | unchanged, now version-checked | Persists the replacement definition at `version + 1`. A stale version is rejected before any mutation. |

`select_project`, `select_goal`, `create_goal`, draft, confirmation and feedback semantics are unchanged. `authorize_adoption` is enabled only where a real adoption proposal exists. `start_assignment` remains rejected with `phase_3_unavailable`.

**A3. Registration is inspect-then-confirm.** An inspection is transient and expires after five minutes (`DEFAULT_REGISTRATION_TTL_MS`). A durable Project exists only after confirmation. Confirmation refuses overlap with the workbench state root in either direction (`unsafe_path`), refuses a path whose Git context moved since inspection (`invalid_input`, "Project Git context changed since inspection"), refuses a duplicate registration, refuses a Project whose storage overlaps an existing Project in either direction, and refuses an unknown or expired `registrationId`. Inspections never appear in `projects` and are never durable evidence.

Registration refusal reasons are runner-computed and rendered verbatim: `not_a_git_worktree`, `bare_repository`, `nested_worktree_or_submodule`, `linked_worktree_or_shared_git_dir`, `unresolved_git_common_dir`. A linked worktree or shared Git directory is refused because the workbench cannot own per-Project storage for a checkout two Projects can share. `nested_worktree_or_submodule` fires when a subdirectory of a repository is selected; selected submodule roots now reject with `submodule_repository`, and an unavailable superproject query rejects with `unresolved_superproject`. Repository replacement at identical paths remains open F9 work. The separate readiness reason `no_head_commit` states that registration succeeded but work cannot start. The presentation never derives either list.

**A4. Check identity and stale edits.** Identity is `(projectId, checkId, version, digest)`. `configure_checks` names the version it edits; the runner rejects a mismatch rather than relabelling old evidence, and the adapter refuses a target with no enabled committed action. `create_check` and `configure_checks` persist; neither executes anything, and a saved definition is not evidence that a check has ever run.

**A5. Adoption is a stage machine over one frozen digest.** A proposal is `proposed`, then `authorized`, `awaiting_ack`, `committed`, `ready`, or `failed`/`expired` (30-second default TTL, at most 16 pending intents). Authorization, acknowledgement, delivery and readiness must each name the exact frozen `proposalDigest`. A mismatched acknowledgement throws `fence_conflict` and never rebinds. Generation is `(projectId, role) high-water + 1` in the retained fence ledger, asserted both when a proposal is created and at the commit boundary. Retirement retains the immutable predecessor and its generation; replacement records a new generation with the predecessor named. Purge is leaf-only across all binding states, including a successor that is already retired, and retains the fence row and high-water mark, so a later adoption cannot reuse a retired generation.

A binding state is one of `proposed`, `authorized`, `acknowledged`, `committed`, `ready`, `manual_takeover`, `manual_takeover_disconnected`, `disconnected`, `retired`, `purged`. The added `manual_takeover_disconnected` state retains control while revoking connection/readiness. Connected manual takeover cannot be retired. `assertLive` refuses any binding management for a fenced, retired or purged Run with `fence_conflict`, so a late `adopt_ack`, `readiness`, `input_observed`, result or takeover frame never mutates a terminal binding.

Acknowledgement carries its own five-second deadline (`DEFAULT_ACK_DEADLINE_MS`), enforced when the frame arrives and by `sweepExpired()`. An acknowledgement that arrives after its deadline is refused with `invalid_input`; the proposal becomes `expired` and the session stays observed. Repeating an acknowledgement after the exchange completed is a stable no-op and never creates a second commit.

Occupancy is any binding for the same Project and Role whose state is neither `retired` nor `purged`, regardless of its connection state. A disconnected, stale or manually taken-over occupant still blocks a new adoption for that Role with `vacancy_occupied`. Goal-scoped occupancy is not implemented in Phase 2: the binding table has no Goal column, so occupancy is Project- and Role-scoped, which violates the required Goal-scoped membership contract and remains an open Phase 2 requirement.

An `input_observed` event whose source is `extension` is recorded as an observation and does not take control. Interactive or operator input takes control: it sets `manual_takeover` and increments that Run's `controlEpoch`. Takeover and disconnect preserve membership, they do not unmanage Pi. Neither delivers an Assignment.

**A5.1 Recovery never invents readiness.** On restart the retained fence ledger wins over store state. A fenced Run becomes `retired` and a purged fence is re-purged. A binding left `acknowledged`, `committed` or `ready` is downgraded to `disconnected` with `writerState: 'uncertain'`, because a restart cannot prove that the Pi side still holds the binding. A `manual_takeover` binding becomes `manual_takeover_disconnected`, preserving the control epoch and uncertainty without claiming connectivity. Challenged surviving-extension recovery remains missing. Recovery reports `retiredFromFence`, `purgedFromFence`, `disconnectedOnRestart` and the uncertain binding ids rather than a silent repair.

**A6. One foreground entry, one line protocol.** `runner/main.ts` is the only entry point. It takes every root as an explicit argument, holds no hidden daemon and opens no socket. `start` writes one record per line to stdout (`ready`, `open`, `projection`, `feedback`, `closed`, `error` or `installation`) and reads one intent per line from stdin, draining each line through the same adapter the QML uses. `inspect` is a read-only Git inspection. `status` and `backup` open an owning runner and advance its epoch, so they are not read-only status calls on an active runner. Native open/hide is not implemented. `backup` reports `restoreSupported: false` and `migrationsSupported: false` rather than imitating a restore.

**A7. Fail-closed protocol boundary.** An unsupported runtime action, a malformed request or a payload outside the closed schema never reaches a mutation. The adapter rejects it, or the entry point reports a record with `code` and `message` and exits non-zero. No refusal is reported as an acknowledgement.
