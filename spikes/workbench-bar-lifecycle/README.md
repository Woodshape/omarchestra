# Local Workbench bar-button installation lifecycle — assessment and resolution

Status: **receipt-owned migration installed; operator confirms physical bar open/Close; foreground owner then intentionally stopped** (2026-09-24). The read-only assessment below records the original blocker, followed by its resolution.

## Question

Can the currently receipt-backed `omarchestra.agent-console` **panel** installation be upgraded to a visible **bar-widget + panel** with the same plugin identity through the installed Omarchy 4.0.4-1 supported enable/put API, without changing the old receipt's exact uninstall/rollback and unrelated-config preservation guarantees?

## Success criteria

One explicit inspect→TTY-authorized update would move exactly the owned plugin entry to `bar.layout`, install the bar widget and dock Close button, and prove rollback/uninstall and interruption recovery restore the prior exact `shell.json` bytes without touching unrelated widgets. The bar button must call the actual foreground owner (and fail visibly if absent) without starting another runner, hidden Pi or shell-script-derived authority. A disposable fake-install matrix and a human live round trip are separate gates.

## Evidence

The current receipt owns a single `plugins[]` entry for `omarchestra.agent-console`; `bar.layout` contains no such widget. The installed shell's `PluginRegistry.setEnabled()` prioritizes the existing `findEntryLocation()` and inserts into `bar.layout` only for an **absent** entry (`!location.found && isBarWidget`). Merely adding a `bar-widget` kind to the manifest and running the existing installer `supportedEnable()` leaves the existing `plugins[]` entry in place: no bar icon appears. `omarchy bar put` delegates to the same `setEnabled()` and cannot migrate this existing panel entry either. `omarchy bar move` requires an already placed bar entry. Disabling the old panel first and enabling the mixed-kind manifest can produce a bar entry, but the current `replace()` does not disable the prior entry and its interruption/rollback/uninstall paths and `shellEntryIsExact` postconditions still assume `plugins[]`. A direct edit or extra unreceipted `omarchy bar put` would make the receipt fail closed on the next update/uninstall; it is **not** authorized by the request to add a button. The current standalone application-menu toggle works but does not satisfy the bar contract.

## Original conclusion

**Unsupported by the then-existing installer; supported with a new installation migration contract.** This is not a package-version pin or a reason to alter historical releases. No bar configuration, installed plugin, shell process or active managed Pi was modified during this initial assessment. The subsequent authorized installation is documented below.
