   Question to answer:                                                                                                                                                                                        
                                                                                                                                                                                                              
   Can Omarchestra use Boomux strictly behind a narrow replaceable terminal-runtime adapter to:                                                                                                               
                                                                                                                                                                                                              
   1. negotiate required capabilities;                                                                                                                                                                        
   2. create one uniquely named Workspace for a Team Goal;                                                                                                                                                    
   3. create three persistent Shells representing Coordinator, Builder, and Reviewer;                                                                                                                         
   4. present all three as native terminal windows under Hyprland;                                                                                                                                            
   5. identify each exact Shell Run and process lifecycle;                                                                                                                                                    
   6. close a terminal window without terminating its process;                                                                                                                                                
   7. present/reopen the exact surviving process;                                                                                                                                                             
   8. observe lifecycle changes through supported snapshots/events;                                                                                                                                           
   9. close only the spike-owned Shells and Workspace safely;                                                                                                                                                 
   10. do all of this without importing Boomux Rust internals, reading private state files, or adopting Boomux entities as Omarchestra domain objects?                                                        
                                                                                                                                                                                                              
   Safety constraints:                                                                                                                                                                                        
                                                                                                                                                                                                              
   - Existing Boomux Workspaces, Shells, agents, configuration, and integrations are user data. Snapshot them before the spike and never modify or close them.                                                
   - Give every spike resource a unique, recognizable prefix.                                                                                                                                                 
   - Cleanup may target only identifiers created and recorded by this spike.                                                                                                                                  
   - Do not run setup, update, uninstall, integration installation, remote Node, web-server, or global cleanup commands.                                                                                      
   - Automated tests must not open GUI terminals unexpectedly.                                                                                                                                                
   - Keep all implementation under spikes/boomux-runtime-adapter unless a small justfile or ignore-file change is required.                                                                                   
   - Do not implement Pi integration, QML, SQLite, production orchestration, or the final runner.                                                                                                             
   - Use public CLI/capability contracts. Treat non-JSON commands explicitly as weaker dependencies.                                                                                                          
   - Build a throwaway adapter and deterministic tests, not production architecture.                                                                                                                          
                                                                                                                                                                                                              
   The spike must define and test this conceptual port:                                                                                                                                                       
                                                                                                                                                                                                              
   capabilities()                                                                                                                                                                                             
   create(session specification) -> terminal session reference                                                                                                                                                
   present(reference)                                                                                                                                                                                         
   inspect(reference) -> lifecycle state                                                                                                                                                                      
   close(reference)                                                                                                                                                                                           
   subscribe(references, cursor) -> ordered lifecycle events                                                                                                                                                  
                                                                                                                                                                                                              
   Automated work must establish:                                                                                                                                                                             
                                                                                                                                                                                                              
   - exact commands and JSON envelopes used;                                                                                                                                                                  
   - capability/version checks and typed failures;                                                                                                                                                            
   - opaque runtime-reference mapping;                                                                                                                                                                        
   - argv construction without shell interpolation;                                                                                                                                                           
   - snapshot/event parsing and cursor behavior;                                                                                                                                                              
   - idempotency and cleanup policy;                                                                                                                                                                          
   - behavior when Boomux or required capabilities are unavailable;                                                                                                                                           
   - a source audit preventing internal-state and Rust-module coupling.                                                                                                                                       
                                                                                                                                                                                                              
   Manual validation must prove:                                                                                                                                                                              
                                                                                                                                                                                                              
   - all three native terminals appear and are tiled;                                                                                                                                                         
   - each represents its expected spike-owned Shell;                                                                                                                                                          
   - closing one terminal leaves its process alive;                                                                                                                                                           
   - presenting it again reconnects to the exact same Shell Run/process;                                                                                                                                      
   - other spike terminals remain unaffected;                                                                                                                                                                 
   - cleanup removes only spike-owned resources.                                                                                                                                                              
                                                                                                                                                                                                              
   Record the question, assumptions, exact versions, commands, evidence, failures, conclusion, design implications, and disposition of every prototype file. Stop at a documented human observation gate      
 rather than claiming GUI, detach, or reconnect behavior from automated tests alone.
